1. Project Summary & USP
Twacha (तvacha — Sanskrit/Hindi for "skin") is a Flutter mobile app that tracks daily skin
health using the smartphone camera, maps skin condition scores to personalized dietary
recommendations, and adjusts advice based on local air quality. Designed and optimized
for the Indian demographic (Fitzpatrick III–VI).

5. Recommendation Engine — How It Works
This is the biggest architectural decision in the project. Here is the complete pipeline, step
by step.
Why not fixed rules?
A fixed rule set ("acne > 6 → show glycemic rule") has two fatal problems:
1. Everyone with the same score gets the same food list, regardless of what they're
already eating.
2. There's a hard ceiling — you can only cover combinations you manually wrote.
Option B — Published coefficient scoring (implemented)
Instead of rules that "fire," every nutrient gets a continuous relevance score computed from
the skin scores using published dermatology coefficients.
Published sources for coefficients:
acne_score × coefficient_for_this_nutrient
+ redness_score × coefficient_for_this_nutrient
+ dryness_score × coefficient_for_this_nutrient
× AQI modifier (for antioxidant nutrients only)
= relevance score for this nutrient

predictor

General dermatology consensus
AQI modifier (applied to antioxidant targets only):
AQI good (0–50): × 1.0
AQI satisfactory (51–100): × 1.1
AQI moderate (101–200): × 1.2
AQI poor (201–300): × 1.4
AQI very poor (301–400): × 1.6
AQI severe (400+): × 1.8
Result: a ranked list of all 10 nutrients with individual scores. No ceiling — any combination
of scores produces a unique ranked list.
Personalization via dietary log filtering
Top 3 nutrient targets are passed to nutrient_lookup.py , which:
1. Returns the master food list for each nutrient (sourced from INDB for micronutrient
rules, GI literature for glycemic rules)
2. Filters out any food the user logged eating in the last 3 days
3. Returns only foods they don't already eat regularly
Example (tested and confirmed working): Rohan logs: white rice, dal, curd, poha. System
fires low_glycemic  target.
White rice: filtered out (already in his log)
Dal: filtered out
Curd: filtered out
Poha: filtered out AND added to reduce list (GI ~70, commonly thought healthy)
Result: recommends rajma, horse gram, chana, jowar roti — things he doesn't eat
Trend layer
Three recommendation layers total:
1. State layer — today's nutrient scores (which target ranks highest)
2. Trend layer — rolling 7-scan window comparison, smoothed:
improving  — current score > 0.5 below rolling average
worsening  — current score > 0.5 above rolling average
flat  — within ±0.5 of rolling average
insufficient_data  — fewer than 3 past scans (first ~7 days)
3. Environmental layer — AQI modifier already baked into nutrient scores; redness +
AQI correlation surfaces antioxidant targets higher automatically
Escalation logic (Phase 2 extension — not yet built)
If a nutrient target has been top-ranked for 7+ days and trend is flat , the system should
diversify to the next-ranked target rather than showing the same recommendation again.
Plan for this before Phase 4 ships.

7. 30-Day Adaptive Program
Program structure — elapsed time, not scan count:
program_start_date  set on first scan
Progress shown as "Day X of 30" regardless of how many scans were done
2–3 day scanning cadence expected; daily not required
Scan gaps are not missing data — last known scores carry forward for trend
Milestone check-ins (Flutter screens should handle these states):
Milestone
What to show
Day 1
Baseline scores; first recommendations; "your 30-day journey starts now"
Day 7
Which metric moved most; trend classification per metric
Day 14
Mid-program summary; escalate if any metric is still flat
Day 30
Full before/after comparison (first scan vs. latest); offer to renew
Smoothing rule (critical for avoiding noise-driven whiplash): Never compare a single
scan to a single past scan. Always compare today's score against the rolling average of the
last 3+ scans. A 3-point spike from bad lighting is noise; a sustained trend over 7+ days is
signal.
Dermatologist escalation note: If redness or acne trend is worsening  for 10+ consecutive
days despite recommendations being followed, surface a note: "This pattern may benefit
from a dermatologist's assessment — dietary changes alone may not be sufficient." This is
the ethical boundary of what the app should claim.
8. Privacy & Image Lifecycle
Core principle: process and discard. Numbers persist; pixels don't.
Lifecycle (enforced in current backend)
There is no image column in the skin_scans  table. This is not an omission — it is the
design. Images cannot be retained because there is nowhere to store them.
User-facing controls (Flutter, Phase 4)
Consent screen before first camera use: "Your photo is analyzed and immediately
deleted. We only keep your skin scores, not the image."
Settings toggle: "Keep my scan photos" — off by default, opt-in only
"Not a medical diagnosis" text visible wherever scores are displayed
1. Image uploaded via POST /api/scan/
2. Read into memory (await image.read())
3. Passed to CV pipeline (mock_cv.py or real model)
4. Score vector extracted
5. Image object goes out of scope → garbage collected
6. SkinScan record saved with scores only — no image field exists
7. API response returns scores — no image field in response
Why this also saves money
Image: 1–5MB per scan. Score record: < 1KB per scan. Over 30 days: ~75–150MB of images
vs. ~30KB of scores. This keeps the app on free-tier hosting for far longer.
Legal note (not legal advice)
India's Digital Personal Data Protection Act (DPDPA) includes data-minimization
principles. "Process and discard" is the correct default posture for biometric-adjacent data
regardless of whether strict compliance is required for a class project.
9. Pollution-Adjusted Skin Insights (New USP)
This is the project's strongest evidence-based differentiator.
Why it's clinically defensible
PM2.5 exposure is significantly associated with increased skin redness area —
confirmed by 2025 imaging-based assessment study
Elevated PM2.5, PM10, and NO2 are associated with increased acne outpatient visits;
pollutants are recognized in the "acne exposome" (2019 dermatology review board)
2025 systematic review confirms consistent pollution-acne associations across PM2.5,
PM10, NO2, and traffic emissions
PM2.5 triggers oxidative stress → depletes antioxidants → vitamin C/E
recommendations are mechanistically justified, not just correlated
This means the pollution USP is in the clinical  evidence tier — stronger than the dairy-
acne link (which is mixed ).
Technical implementation
Data: WAQI API — free token, covers 1000+ Indian cities
City-level only: never request precise GPS. AQI is a city/station metric anyway; fine-
grained location adds no accuracy and adds privacy risk
AQI modifier in recommender.py : automatically amplifies antioxidant nutrient targets
(vit C, vit E) by 1.2–1.8× when AQI is above moderate
Smoothing: rolling 3–7 day AQI average, same as scan trend — one bad air day
shouldn't whiplash the recommendations
What the user sees
When AQI is poor  or worse for multiple days:
AQI badge on dashboard turns red with a short note
antioxidant_vit_c  and antioxidant_vit_e  targets score higher automatically →
amla, guava, drumstick leaves, almonds surface
Card text explicitly links the AQI to the recommendation: "Bhopal's air quality has
been poor this week. PM2.5 at this level depletes your skin's antioxidant reserves —
these foods help replenish them."

14. Evaluation Plan
CV model (Phase 3):
Primary metric: intraclass correlation coefficient (ICC) between model severity scores
and dermatologist-graded severity on a held-out ACNE04 test split
Fairness check: compare model accuracy across ITA ranges on the DermaCon-IN
validation subset — flag if lighter-skin ITA bands score significantly better
Recommender (Phase 2):
Manual review: domain-literate reviewer (nutrition/derm student is sufficient) checks
each of the 10 nutrient targets and their food lists before scaling
Logic test: force fixed score vectors (e.g., acne=9, redness=2, dryness=2) and confirm
glycemic target ranks first; (acne=2, redness=9, dryness=2) confirms
omega3/antioxidant rank first
End-to-end (Phase 4):
5–10 test users doing the full 30-day program
Collect: scan scores over time, dietary logs, subjective skin rating
Report: did scores trend downward for users who followed recommendations? Is there
a measurable difference between users who logged diet vs. those who didn't (dietary
filtering active vs. inactive)?
